## Rule 6 is why this exists

Every online geocoder and every tile map sends the photo's coordinates to a server. That
includes `CLGeocoder`, MapKit, Bing, OSM tiles and Google. So places are computed from data
shipped on the machine. Nothing in `src/geo` opens a socket, and the data build is the only
step that downloads anything. It runs at package time, from pinned URLs.

## Module

`src/geo` is portable C++ (D9). It contains no platform API.

| File | What |
|---|---|
| `geo.h` / `geo.cpp` | `database`: validate a blob, `lookup(lat, lon)`, `match(text)`, polygon and ring access for the map |
| `blob.h` | The on-disk format, as POD records with pinned sizes |
| `fold.h` | The case and diacritic fold: `core/fold.h`'s rule, shared with file search and Local search (#291). The table is `src/core/fold_table.inc`, generated by `tools/fold/gen_fold_table.py` |
| `open.h` / `open.cpp` | `open_database(path)` maps a file through `io/mapped_file`. Also `set_data_path` / `shared()`, one database per process |

`geo.cpp` and `fold.cpp` include only core's header-only pieces (`result.h`, `status.h`). The
CMake target `mv_geo` is therefore position-independent and links nothing of the core, so an
add-on can link it (add-ons link nothing of the core: [18-import.md](18-import.md)). `open.cpp`
is `mv_geo_open`, which uses `mv_io`, for tests, tools and any in-process host.

`tools/check-module-graph.ps1` gives `geo` the dependencies `{geo, io, core}` and lets `addons`
include it. **`meta`, `abi` and `shell` may not include it.** Places arrive through the add-on,
never wired into the app. `io/mapped_file.h` is a new port: `mapped_file_posix.cpp` (`mmap`
with `MADV_WILLNEED`) and `mapped_file_win.cpp` (`CreateFileMappingW` / `MapViewOfFile`).

```cpp
namespace mv::geo {
struct lookup_options { double town_radius_km = 15; bool native_names = false; };
struct place { std::string town, region, country, country_code, region_code;
               bool at_sea; double town_km; std::string label; };
struct name_match { name_kind kind; bool exact; std::string country_code, region_code, name; };
class database {
  static result<database> from_bytes(std::span<const std::uint8_t>, bool verify_checksum = true);
  place lookup(double lat, double lon, const lookup_options& = {}) const;
  std::vector<name_match> match(std::string_view text, bool prefix = false) const;
  std::vector<std::uint32_t> polygons_in(layer, const box&) const;     // slice 3
  std::size_t ring_count(layer, std::uint32_t) const;
  std::span<const point> ring(layer, std::uint32_t polygon, std::size_t i) const;
  std::string_view polygon_country_code(layer, std::uint32_t) const;
  std::vector<town_ref> towns_in(const box&, std::size_t limit) const; // map town dots, by population
  std::string_view meta() const;                                       // provenance JSON
};
result<std::unique_ptr<mapped_database>> open_database(std::string_view utf8_path);
void set_data_path(std::string_view);  const database* shared();
}
```

A `database` is immutable once it opens, so concurrent `const` calls from workers are safe.
Opening is I/O and belongs on a worker. A lookup takes microseconds, but it still belongs on a
worker (rule 1).

## The data

`tools/geo/build_places.py` uses the standard library only, so packaging CI needs no pip
install. Its inputs are pinned by URL and SHA-256. Downloads go to a directory the caller
names, never the source tree:

| Input | Licence | Pin |
|---|---|---|
| Natural Earth 1:10m admin-0 countries, admin-1 states/provinces (GeoJSON) | Public domain | `nvkelso/natural-earth-vector` tag v5.1.2, commit `f1890d9f` |
| GeoNames `cities1000`, `countryInfo.txt`, `admin1CodesASCII.txt` | CC-BY 4.0 | Snapshot of 2026-10-11 |

GeoNames republishes its dump every day under the same URL, so its pins go stale. A changed
file stops the build unless `--accept-upstream` is given. That flag takes the new file and
prints the hash to pin. The blob's `META` section records every input's hash, so a build can
always be traced to its data. Mirroring the pinned snapshot as a release asset of this repo
would make packaging fully reproducible. That is an owner call (below).

**Polygons.** Both layers are simplified with Douglas–Peucker so that shared topology is
preserved:
- Each ring is split wherever the set of features owning a vertex changes.
- Each arc is simplified once, in a canonical direction, and the result is reused by every
  feature that shares it. Enclave rings are canonicalised by rotation and orientation.
- So a border is the same line for both neighbours. There are no gaps and no overlaps between
  countries or regions.
- Coast arcs use a 1 km tolerance and shared borders 250 m. A ring that would collapse keeps a
  minimal shape.

Points are int32 microdegrees, and every ring is stored closed. Each polygon also gets:
- a bounding box;
- a list of the edges that meet each 1° latitude band;
- a place in a 1° grid of candidate polygons. A cell no edge crosses is flagged **full**, and a
  point there needs no ray cast.

**Regions** are GeoNames admin-1, so a town's own admin-1 code and the polygon agree. Natural
Earth divides some countries more finely than GeoNames' first level: French départements, UK
councils, old Luxembourg districts. So each Natural Earth admin-1 feature is mapped to a
GeoNames code:
- Natural Earth's own `gn_a1_code` wins when it is a valid code and a town inside the feature
  confirms it.
- Otherwise, the up to 40 towns inside the feature vote, weighted by population. The capital
  beats the suburbs that simplification lets in at the edge.
- A feature split between several GeoNames codes with no majority (all of Puerto Rico against
  its 78 municipalities) becomes a Natural Earth-only region with no code.
- Where at least 80% of the town weight belongs to another country, the region carries
  `k_region_country`. GeoNames files Svalbard (`SJ`) and Réunion (`RE`) as countries, while
  Natural Earth draws them inside Norway and France. The region's country then wins.

**Towns.** GeoNames populated places, excluding:
- `PPLX` sections of a city;
- `PPLA5` (the Paris arrondissements);
- historical, abandoned, destroyed and religious places.

That leaves 161 600 places. Each record holds the name, population, country and region, sorted
into the 1° grid.

**Names people type.** For countries: the English name, the native name (Natural Earth's
`NAME_<lang>` for the country's first GeoNames language), and Natural Earth's names in about 25
languages ("Portugália"). For regions: the GeoNames name and ASCII name. Natural Earth's names
are added only when the feature *is* the region, so a département's name never finds its whole
région. Full GeoNames alternate names (~600 MB) stay out of scope.

### Blob format (`places.mvgeo`, version 1)

The file starts with a 64-byte header: magic `MVGEO\x1a`, version, file size and checksum. A
table of sections follows, each 8-byte aligned and little-endian:
- strings;
- countries (16 B);
- regions (16 B);
- towns (20 B) and their grid;
- META (JSON);
- per layer: polygons (40 B), ring starts, points, band offsets, band edges, grid rows (sparse:
  a row stores only its used column span), cell offsets and candidates.

The checksum is a four-lane 64-bit multiply-xor over everything after the header. The loader
(`from_bytes`) bounds-checks every offset, count, index, edge and grid run once, and requires
every point to lie on the globe, so the 64-bit crossing test cannot overflow. After that the
lookups run unchecked. A truncated, damaged or foreign file is `status::corrupt`, and a newer
format is `unsupported_format`.

The full blob is **17.2 MB** raw and **5.4 MB** xz-compressed, close to the plan's ~6 MB
target. It holds:
- 256 countries;
- 3 931 regions;
- 161 600 towns;
- 230 k admin-0 points and 639 k admin-1 points.

## The label rule

1. **Country.** This is the admin-0 polygon that contains the point.
   - Not inside any polygon but within **1.5 km** of one (`k_coast_snap_km`): on land in that
     country. This covers a beach, a pier or a harbour wall that simplification moved offshore.
   - Else within **2 km** of a town (`k_town_land_km`): on land in the town's country. Atolls
     such as Tarawa are narrower than the data.
   - Else within **25 km** of land (`k_off_coast_km`): "At sea, off Portugal". Otherwise
     "At sea".
2. **Region.** This is the admin-1 polygon, or the nearest one within the snap distance. It is
   kept only if it belongs to the country. A `k_region_country` region overrides the country.
   With no region polygon, the chosen town's own region is used.
3. **Town.** Candidates are the towns of the same country, and of the same region when that
   region is a GeoNames region, within **15 km** (`k_town_radius_km`, a setting).
   - A town *reaches* `sqrt(population / (π · 5000/km²))`: a city of 500 k reaches about
     5.6 km, and 8 million about 23 km.
   - If the point is inside one or more towns' reach, the town it is deepest inside (smallest
     distance / reach) names it. Otherwise the nearest town names it.
   - This puts the Eiffel Tower in Paris and Times Square in New York City, not across the
     Hudson in Weehawken, and central Manila in Manila rather than the larger Quezon City.
   - A town of the right country and region is never dropped for a nearer one across a border.
4. **Label.** "Town, Region, Country", skipping a part that is empty or repeats its
   neighbour: "Madrid, Spain", "Zagreb, Croatia", "Saint-Denis, Reunion".

Plan examples, and what they give:
- "Sintra, Lisbon, Portugal". The plan's "Douro, Portugal" comes out as the district: there is
  no "Douro" admin-1, so it reads "Vila Real" or "Porto".
- The minimum on land is just the country.

The poles are clamped and longitudes wrapped, so -539.95 is 179.95° W. Natural Earth splits
features at ±180°, and the town and coast searches wrap their grid columns.

**The town radius (owner call in the plan).** 15 km is kept. On the 300-row table, the named
towns that lie more than 7.5 km away fall into two groups:
- **Big cities, named by the reach rule:** Dubai 13.8 km, Bogotá 11.3, Dhaka 11.1, Quito 8.4,
  Lagos 8.0. GeoNames puts these cities' points far from their edges.
- **Nearest-town fallbacks:** Uluru → Yulara at 12.5 km, the 49th parallel → Delta at 10 km,
  San Ysidro → Imperial Beach at 8.2 km.

A 10 km radius would drop "Yulara" from Uluru, which is the town every visitor stays in.
Something like 25 km would start naming places half an hour away in empty country. Past the
radius the label drops to "Region, Country". The reach rule, not the radius, is what fixed
the city cases. The radius is a setting (below).

## Matching place names (slice 4)

`match(text, prefix)` folds the text with `geo::fold` and returns the countries and regions
whose folded names equal it, or start with it when `prefix` is set. Exact matches come first.

The fold is the hosts' name fold (`FoldName` in `IslandHost.FileSearch.cs`; Swift
`.caseInsensitive, .diacriticInsensitive`):
- decompose, drop non-spacing marks, lowercase;
- letters with no decomposition (ł, ø, ß) stay as they are;
- it covers Latin, Greek and Cyrillic.

The AI add-on's Latin-1-only `fold` in `src/addons/ai/query.cpp` is older and differs (ß → ss).
Slice 4 should move it onto `geo::fold`. Country codes are not indexed as names, so `PT` does
not match "pt" in a file name.

## Performance

Measured on an Apple M-series machine, Release, warm page cache, with
`mv_tests "[.perf-bench]"`, three runs:

| | Result | Target |
|---|---|---|
| Open (map + checksum + validate + fold the names) | median 11.1–12.1 ms | < 30 ms |
| Lookup, the 300 table rows | p50 2.0 µs, p99 8.4 µs, max 13 µs | < 50 µs |
| Lookup, 2 000 random points (mostly sea) | p50 0.1 µs, p99 3.2–4.1 µs, max 52 µs once | < 50 µs |

file not in the page cache, is not measured. `MADV_WILLNEED` turns the first touch into
read-ahead (17 MB). Windows is not measured; it builds in CI only from this machine. Nothing
here runs on the viewer's paths, so first pixel and arrow → next photo cannot change.

### The pane section

The section is the pane's last thing, below the footer, on every tab, whenever the file has
coordinates (#348, owner 2026-10-12). The host asks `info_section` on the add-on's worker with
the file's location, its own coordinate text, the theme tokens, the pane's content width and the
backing scale; Places answers with one view tree and one surface:

1. a title text: the place label ("Sintra, Lisbon, Portugal"), copyable;
2. a secondary text: the host's coordinates, copyable;
3. a 160 pt `surface` "map": the picture, a `pin` at the photo's point (the chrome draws it in the
   accent colour with a soft shadow and a drop-in Reduced Motion turns off), `marks` (town names)
   and `interactive` bounds. It is one accessibility element labelled "Map of <place>";
4. a row: the caption "No street detail — offline map", and Zoom out / Zoom in buttons
   (`minus` / `plus`), each disabled at its end of the range;
5. for a file that has a folder, the **This folder** toggle ([below](#the-folder-map-601)).

Neither host has Places-specific code: they render the tree, the BGRA surface, the pin and the
marks, and drop a stale generation. A file whose location changes (#352's editor) is a new info
request, so the label and the map follow it; only pictures are cached, by point.

### The map

Drawn by the add-on on its worker into 8-bit BGRA, premultiplied, at the pane's width × 160 pt
times the backing scale (`map.cpp`). The host takes 4096 px a side at most, so a very wide pane on
a 3× display gets a lower backing scale (1600 pt → 2.56×), never a missing map.

- **Projection.** Web Mercator, centred on the view's centre, with the view's `span_deg` as the
  picture's height in degrees of latitude there. Each ring is unwrapped from its own first point
  and drawn at every whole-world shift that reaches the picture, so a ring near the antimeridian
  is whole whichever side of 180° the view is on. Antarctica, one ring that goes once round the
  globe, is closed through the South Pole beyond the picture's edge.
- **Fill.** Land is a signed-area accumulation (the font-rs method), each polygon oriented so its
  outer ring is positive and folded even-odd so lakes and enclaves stay open. Anti-aliased, and two
  countries sharing a border add up to full coverage with no hairline between them. The photo's
  country is drawn in `land_home`, the rest in `land`.
- **Borders.** An edge is a land border exactly when two polygons share it: the database
  simplifies each shared arc once for both neighbours, so a border edge appears twice and a coast
  edge once. Coasts are never stroked (a narrow estuary stays a coast). Country borders 0.6 pt,
  admin-1 borders 0.35 pt at a span of 9° or less where the picture holds at most 48 regions
  (US states) and from 4.5° where it holds more (French départements). Natural Earth's cut at
  ±180° is not a border.
- **Towns.** From a span of 9° down, cities1000 towns over `1000 · (span / 0.2°)^1.5` people
  (about 300 000 at 9°, every town at 0.2°), most populous first, at most 48, none within 14 pt of
  a bigger one. Each is a dot with a land-coloured halo; the first 16 names go out as `marks` for
  the chrome to set in its own caption font.
- **Frame.** 8 pt rounded corners (transparent) and a hairline in the theme's hairline colour.
- **Colours** come from the host's tokens, light and dark: `land_home` lifts the pane's surface
  toward white, `land` is a little greyer, water is a quiet blue mixed into the surface, borders
  and town dots are the body / title text at low weight. A theme change is a new picture.
- **Cache.** The last 12 pictures by (centre, span, size, scale, palette, country), so arrowing
  back or zooming out and in again does not redraw. A hit costs ~0.03 µs.

**Zooming the map** (owner, 2026-10-12). Over the map a trackpad pinch or a mouse wheel zooms
about the cursor, a drag pans, a double-click zooms one step in about the click, and −/+ (and the
keyboard, which presses them) step about the centre. A trackpad two-finger scroll is not taken:
it keeps scrolling the pane. The chrome shows pinch, wheel and drag live by moving the last
picture (bitmap, pin and marks together, chrome only: no present), and sends one event when the
gesture settles (`MV_SLOT_EVENT_ZOOM {scale, x, y}`, `PAN {dx, dy}`, `DOUBLE {x, y}`). Places
turns that into a view with `apply_gesture`: a point at normalised p now shows at
`anchor + (p − anchor) · scale + pan`, at exactly the pixel scale the gesture showed (so the new
picture lands where the transform left it), then clamped:

- the span to [0.2°, 40°], town scale to the whole of a large country, and the live transform to
  the same range (`interactive.min_scale` / `max_scale`);
- the centre so the photo's point stays inside the picture with an 8 % margin: the pin never
  leaves it.

It re-draws, posts the surface, then a diff moving the pin and marks and the buttons' state (the
chrome drops its transform when the surface's revision moves). A newer gesture arrives as a newer
delta on the state it left.

### The folder map (#601)

A **This folder** toggle under the map (a `toggle` node, `folder`, shown for a file that has a
folder: not a Photos library item) draws every geotagged item of the open folder on the same map.
It is read-only: picking a point on the map to *write* coordinates is a different, backlogged
feature ([06](06-metadata.md)).

- **One choice for the session.** The toggle is the engine's, not a setting: it stays on as the
  person arrows through the folder and into the next one, and starts off in a new process.
- **Where the points come from.** Turning it on (or the section asked for a file of a folder not
  read yet) walks the folder with the host table's `locations_in`, under the section's generation:
  the host's metadata cache serves it, so a folder the viewer has shown costs no read, and a walk
  for a file the person has already left stops (`MV_ERR_CANCELLED`) and draws nothing. The section
  is posted first; the dots follow once the folder is read. The points are kept per folder
  (`folder_points`, at most 50 000), so arrowing within it reads nothing; a geotagged file the
  held list lacks (new since) reads the folder again.
- **Dots and clusters** (`folder_map.h/.cpp`, a layer over the picture; the base stays in the
  cache and the dots go into a copy). Each item is projected with `map_pixel`'s projection, built
  once per picture, and binned into a grid of 22 pt cells anchored to 0°/0° (so a pan, which keeps
  the pixel scale, keeps every cluster's members). A cell is one dot at its items' mean; dots of
  neighbouring cells that would overlap are merged once, the bigger taking the smaller. A lone
  item is a 3.5 pt dot; a cluster grows with log₂ of its count to 8.5 pt and has a light centre.
  The fill is the accent mixed toward the title text (never the pin's own colour), ringed in the
  land colour so it reads on any border. **The current item is the pin**, never a dot.
- **A click opens a dot's file.** Both hosts report a single click on an interactive surface as
  `MV_SLOT_EVENT_TAP {x, y}` (#601; WinUI `Tapped`, past which a drag is not a tap; SwiftUI's
  single tap after the double-tap fails). Places finds the dot under it (its radius plus 5 pt;
  the nearest edge wins) and asks the host to show that item, or a cluster's first in folder
  order, through the host table's `open_item` (appended after `still_write`). The registry takes
  only a file of the folder of the file on screen, for the section's current generation, and
  carries it in `info_json`'s `"open": {path, revision}` until the next file is asked for; each
  chrome opens it once per revision, and only if its listing holds that path (Windows:
  `SelectItem` on the strip index; Mac: `FolderStore.select(path:)`). The opened file asks the
  section again, so the pin moves to it and the old one becomes a dot. A click off every dot does
  nothing; the first click of a double-click on Windows is a click too (it opens only over a dot).
- **Idle.** Nothing ticks: the layer is drawn once per section, toggle, gesture or folder read,
  on the add-on's worker, and the chrome shows the posted pixels. With the section shown and
  nothing moving, the canvas presents nothing.

Measured (2026-11-02, Linux container shared with other builds, g++ 13 `-O2`,
`mv_tests "places: the folder map over 600 geotagged items at 2x"` in `[.perf-bench]`; 600 items

| | Median | p90 | Max |
|---|---|---|---|
| Dot layer CPU (cluster + copy the base + draw) | 0.27–0.29 ms | 0.50–0.53 ms | 0.94–1.12 ms |
| Clustering alone (wall, one run) | 30 µs | 42 µs | 64 µs |
| Base map + dot layer CPU (a cache miss), on the **test** blob | 6.0–6.3 ms | 6.6–7.6 ms | 7.6–8.9 ms |
| Engine refresh at the section's view (base a cache hit) | 0.27–0.31 ms | 0.29–0.39 ms | 0.48–0.56 ms |

### The world map

Places' own window, `world` (contribution API 12; `docs/plans/places-world-map.md`, owner
2026-11-04): the same offline map filling a resizable window that goes full screen (the green
button on the Mac, F11 on Windows), from the whole world down to the section's town scale, with
every geotagged item of the **library** on it. It opens from **Open map** under the section's map
and from the command bar (**World Map**). Read-only, offline, nothing leaves the machine.

- **What it shows.** Every asset of the Local search index with coordinates
  (`locations_of_index`, index.db's own lat / lon: no file read); a clip is one dot at its first
  fix (`ROUTE_POINT` rows are skipped). Without the AI pack, or when nothing indexed has a place,
  it shows the folder of the file on screen (`locations_in`) and says so. At most 400 000 items,
  kept compact (`world_points`: points apart from one buffer of paths). The file on screen when
  it opened is the pin.
- **The view** (`world_map.h/.cpp`). The section's projection and renderer, with the span cap a
  field of the view (`map_view::max_span_deg`): the widest span is the one where the world's width
  fills the picture's (`360 · H · cos(lat) / W`), and the last step out sits on the equator. The
  first view frames the library's box (across 180° when that is narrower). A resize keeps the
  ground per point. The backing scale is the display's, lowered so each side stays within
  4096 px and the picture within 8 MP (a full-screen 5K window draws at about 1.5×).
- **The surface fills** its window (`"fill": true`) and the chrome reports its laid-out size as
  `MV_SLOT_EVENT_RESIZE` once a resize settles; the registry coalesces a run of them. The gestures
  are the section's (pinch, wheel, drag, double-click, −/+); on the Mac a trackpad two-finger
  scroll pans too, as nothing scrolls there.
- **Dots** are the folder map's (`cluster_points`, the same grid and merge as `cluster_dots`,
  with each point's dot for a click). **A click on a dot** shows its items (walk order, at most
  10 000) in the viewer as a result list titled with the first item's place and the count
  ("Sintra, Lisbon, Portugal (3)"), through the host table's `open_list`; the viewer comes
  forward and the map stays open behind it.
- **Idle.** Nothing ticks; closing the window drops the library's points and its picture cache.

Measured (2026-11-04, M-series Mac, Release, the full place blob from the installed add-on,

### Search by place

The same add-on's search provider, `place:` and `in:` (#348 routes `in:` followed by a digit to
everyone, so `in:2024` stays Local search's date term; #291's parser reads `in:<word>` as a date
when it parses as one). For a folder it walks the host's cached `locations_in`, looks each file
up and posts rows in batches of 128 with the file's place label as the `why`. The rule
(`place_query`): the folded query equals a country's or region's name in any of the database's
languages, or starts one at 4 letters or more ("portu" finds Portugal while typing, "po" does
not); or it equals the file's own town (starts it, at 4 letters). A point at sea is in no country.
A query starting with a digit is never a place. A Local search request (folder "") walks the
host table's `locations_of_index` instead (#398): the AI pack's index.db coordinates, streamed
with no file read, under the same rule and the same batches. A host without that row, or with no
AI pack loaded, gets `done` with no rows.

In Local search the provider is asked by the AI pack, not beside it (#441). For each place term
(`place:portugal`, `in:lisbon`, `-place:spain`) the pack's engine calls the host table's
`place_matches`, which sends Places one request for that word over the whole index and hands
back every row's path once Places posts done. The engine intersects those assets with the rest of
the query, so `beach place:portugal` is Portugal's beaches and nothing else (doc 17 "Places over
the index"). Local search sends a query with place terms to no other provider, so there is no
"+ N in Portugal" beside the list. **Without Places a place term matches nothing**: the core has
no borders, so the search panel says "Place search needs the Places add-on. Install it from
Settings → Add-ons", and its help line leaves `place:` out while Places is not loaded. File search
(the path bar's field) routes `place:` to Places as before.

### Routes (#606)

A GoPro or DJI clip has no ISO 6709 tag; its position is the first fix of the GPS route in its
telemetry ([06](06-metadata.md) "Telemetry routes"), so it gets a Place section, a label and a
pin like a photo. The rest of the route reaches Places through the host table:

- **`route_of(path, out, capacity, &count)`** (appended after `still_write`): the route, read
  whole from the telemetry track and thinned to `capacity` points evenly spaced, the first and
  last kept (`meta::read_route`; each host installs it through `abi/addon_media`). A still is
  answered from its first kilobyte, with no FFmpeg open; a clip with no fix is 0 points. The host
  keeps its last 32 answers by path, size, mtime and capacity, so asking again (a theme change, a
  later search) is a lookup.
- **`mv_addon_location.has` is a bit set** (`MV_ADDON_LOCATION_*`): `HAS` as before; `ROUTE` on
  a clip whose position is a route's first fix (`location_of`, `locations_in`, from
  meta_cache.db's `has_route`); `ROUTE_POINT` on a row that is one more point of the previous
  row's route, under the same path (`locations_of_index`, from the AI pack's `tracks`). `HAS` is
  set on every row with coordinates, so a reader that only knows `has != 0` takes a route point as
  one more position of that path.

**On the map.** The section asks `route_of` (up to 4 096 points) for the file on screen when the
map is on. `draw_route` (`map.cpp`) draws it over the cached picture, on a copy: a 2 pt line in
the theme's accent (the pin's colour) on a 1 pt casing in the pane's surface colour, anti-aliased,
inside the frame's rounded corners, longitudes unwrapped point to point so a route across 180° is
one line; points that do not move half a pixel are skipped. The base picture stays in the cache
as before, and the engine keeps the last routed picture beside it, so zooming back to it or a
re-ask does not draw it again. The first view (`frame_route`) is centred on the route's box and
widened, never narrowed, until the route shows whole with a quarter more round it, within the
map's range; the pin stays on the picture.

**In search.** By folder (`locations_in`), a file whose own position does not match and whose
row says `ROUTE` has its route asked for (128 points, about one a kilometre on a two-hour drive)
and looked up point by point (`route_why`); the first point in the place gives the result's
`why`. Over the whole index (`locations_of_index`), the AI pack streams a clip's stored track
(schema 11, [17](17-local-ai-search.md)) as `ROUTE_POINT` rows after its own, so no file is
read; Places looks each up until one matches and skips the rest of that path. So `place:spain`
finds a drive that starts in Lisbon and ends in Badajoz.

### Settings (PR 56 schema)

**Offered before it is installed.** Settings → Add-ons lists Places on both hosts even when it
is not there. The line says it is optional and preferred, and that a geotagged photo still shows
its coordinates. Install, update and remove use the same release channel as Import
(`releases/latest`, manifest and signature first). A fresh install loads at once. An update of a
copy this process is already running waits for a restart. "Remove everything" forgets the
settings page; "Remove, keep its data" keeps the user's index and the page.

One page, "Place" (in `manifest.json`):
- `show_map`: toggle, default on.
- `show_town`: toggle, default on.
- `town_radius_km`: number 1–50 km, default 15, `enabled_by: show_town`.
- `label_names`: `english` | `local`.

Read through the host table's `settings_get` on every info request, search and map event (the
store's cache answers, no disk read), mapped onto `lookup_options` (`town_radius_km`, 0 when
`show_town` is off; `native_names`) and the map's presence. Nothing is kept across a change.

**Settings take effect immediately.** Changing one in Settings re-asks the Place section for the
file on screen, once, under a new generation (docs/design/25 "A changed setting re-asks"): the
label, the town and the map follow the new value without moving to another file. A zoom or pan
meant for the old answer is dropped. The map cache keys on point, size, theme, zoom and home
country; no setting changes the pixels (`show_map` only decides whether there is a picture; town
marks are GeoNames' names whatever `label_names` says). Results already listed by file search
are not re-run; the next query uses the new radius. A host without PR 56 refuses a manifest that
names a settings page, so the add-on needs PR 56 and #348 both.

## Known limits

- Natural Earth 1:10m does not draw micro-enclaves: Baarle-Hertog, Campione d'Italia, Büsingen.
  A point there gets the surrounding country. Llívia (13 km²) is drawn.
- Borders are good to about 1 km, so a point within that of a border can land on the wrong side.
- Names are GeoNames' English names: "Sevilla", "Lazio", "Baladiyat ad Dawhah", "State of
  Berlin". Country names are English, or native with `native_names`.
- Towns are populated places of 1 000 people or more. A hamlet reads as its nearest town or
  as "Region, Country".
- The map has no streets, rivers, roads or terrain, and no labels but town names; at town scale
  the coast shows its ~1 km simplification. Inland at region scale (Colorado) it can be nearly
  blank but for borders and dots.
- A route is searched at 128 points (folder) or the index's 128 (Local search), evenly spaced:
  a place the route crosses for less than the spacing (a corner of a region on a long drive) can
  be missed. A route longer than the map's widest view (40°) shows its part around the pin.
